common-authorization ​

Permission management for the Kalisio ekosystem.

Overview ​

@kalisio/common-authorization provides utilities and runtime components for defining, managing, and evaluating authorization rules across frontend applications, backend services, and MCP servers.

TIP

common-authorization builds on CASL and provides a MongoDB-compatible condition matcher for consistent permission evaluation and query generation within its supported subset.

It is organized around two modules:

  • utilities — Stateless helpers for creating and manipulating abilities, evaluating permissions, and generating MongoDB queries.
  • runtime — Stateful components for managing role hierarchies, and authorization, including ability caching.

The authorization model relies on the following concepts:

ConceptDescription
ActorThe identity performing an action, such as a user, service, application, or agent.
AbilityA set of authorization rules associated with an actor.
RuleA definition allowing or denying an action on a subject.
ActionThe operation to perform.
Subject typeThe type of resource targeted by an action.
SubjectThe resource instance targeted by an action.
ConditionsConstraints determining whether a rule applies to a subject.
FieldsSubject properties targeted by a rule.
RoleA named responsibility that can inherit from other roles.
AttributesAdditional subject properties supplied during permission evaluation.

INFO

The package exposes native CASL abilities and builders with a common configuration for condition matching, field matching, and action resolution.

} from '@kalisio/common-authorization'

Usage ​

Defining abilities ​

Use abilities to create and update authorization abilities, define action aliases, and combine conditions.

js
const aliases = {
  read: ['get', 'find'],
  update: ['patch']
}
const { can, cannot, build } = abilities.createBuilder({ aliases })

can('read', 'projects')
can('update', 'projects', { ownerId: 'user-1' })
cannot('update', 'projects', { locked: true })

const ability = build()

Rules support MongoDB-style conditions, logical operators, and field-level restrictions. The last applicable rule takes precedence.

Evaluating permissions ​

Use permissions to evaluate authorization rules against resource types, resource instances, or individual fields.

js
const project = { ownerId: 'user-1', locked: false }

permissions.can(ability, 'find', 'projects') // true
permissions.can(ability, 'patch', 'projects', project) // true
permissions.cannot(ability, 'remove', 'projects', project) // true

Additional attributes can enrich a subject without modifying the original object.

Generating MongoDB queries ​

Use permissions.toMongoQuery() to restrict database queries to authorized documents.

js
const query = permissions.toMongoQuery(ability, 'update', 'projects')
  • null — No document is authorized; do not execute the query.
  • {} — All documents are authorized for this action (and field, if specified).
  • A non-empty MongoDB filter — Only matching documents are authorized.

Authorization filters can be combined with application filters using $and.

Managing roles ​

Use RoleRegistry to define and resolve role hierarchies.

js
const roles = new RoleRegistry()

roles.register('member', {})
roles.register('manager', { inherits: ['member'] })
roles.register('owner', { inherits: ['manager'] })

roles.resolve(['owner'])
// ['member', 'manager', 'owner']

Roles support multiple inheritance. Each role is resolved once, with ancestors preceding their descendants.

Managing authorization ​

Use Authorization to centralize role management and ability computation. Authorization hooks allow application modules to contribute permission rules independently.

js
const authorization = new Authorization({
  aliases: {
    read: ['get', 'find'],
    update: ['patch']
  },
  cache: {
    key: actor => [actor._id],
    max: 1000,
    ttl: 60000
  }
})

authorization.roles.register('member', {})
authorization.roles.register('manager', { inherits: ['member'] })

authorization.registerHook('projects', async (actor, { defineRoleAbilities }) => {
  for (const organization of actor.organizations) {
    await defineRoleAbilities(organization.role, {
      member: ({ can }) => can('read', 'projects'),
      manager: ({ can }) => can('update', 'projects')
    }, { organizationId: organization._id })
  }
})

const actor = {
  _id: 'user-1',
  organizations: [
    { _id: 'org-1', role: 'manager' },
    { _id: 'org-2', role: 'member' }
  ]
}

const actorAbility = await authorization.getAbility(actor)

permissions.can(actorAbility, 'patch', 'projects', {
  organizationId: 'org-1'
}) // true

permissions.can(actorAbility, 'patch', 'projects', {
  organizationId: 'org-2'
}) // false

Authorization supports synchronous and asynchronous hooks, scoped permissions, and optional caching with LRU eviction and expiration. Changes to roles or hooks make cached rules stale. Applications can explicitly invalidate cached rules when an actor's permissions change.
